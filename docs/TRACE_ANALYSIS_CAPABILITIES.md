## How to use these views

**Zephyr CPU Load:** Choose **Window > Show View > Zephyr CPU Load**, select an imported Zephyr project and explicitly load a saved `trace-*/ctf` folder; its table shows per-thread Running percentages and separately labelled ISR time for the selected nanosecond window. It does not show physical CPU utilization, prove missing scheduler events, or infer idle time from an unobserved interval. Enable `CONFIG_TRACING=y`, `CONFIG_TRACING_CTF=y`, a suitable CTF backend such as `CONFIG_TRACING_BACKEND_RAM=y`, and the selected Zephyr revision's actual thread switch tracing hooks before capturing the trace.

**Zephyr Contention Report:** Choose **Window > Show View > Zephyr Contention Report**, explicitly load a saved CTF folder, and adjust the visible long-wait threshold to see evidenced priority-inversion and bounded resource-wait rows. It does not infer an unknown mutex holder, reconstruct absent priorities, or prove a missed deadline. Enable `CONFIG_TRACING=y`, `CONFIG_TRACING_CTF=y`, a supported CTF backend, and the actual mutex/semaphore and thread scheduling trace events available in the selected Zephyr build.

The **Zephyr Workbench** preference page contains **Enable Zephyr CPU Load view** and **Enable Zephyr Contention Report view** (both on by default); disabling either prevents analysis without preventing the Eclipse Show View registration. Both views are passive until **Load trace...** is explicitly selected, and missing Python/bt2, unreadable CTF files, and incomplete decoder evidence are reported rather than silently rendered as empty success.

### JSON boundary (saved CTF, on demand)

The additive `offline_trace_json.py` adapter prints one bounded JSON object to stdout after explicitly loading a saved CTF directory. Both variants include `schema_version: int=1`, `kind: string`, `status: "ok"|"incomplete"|"no_scheduler"` (`no_scheduler` is CPU only), `incomplete: bool`, `reason: string`, and nullable `first_timestamp_ns`/`last_timestamp_ns` integers.

- CPU variant: `start_ns: int|null`, `end_ns: int|null`, `scheduler_events: int`, `cpu: {status: string, cpu_busy_percent: number|null, unknown_ns: int|null, rows: [{name: string, running_ns: int, percentage: number}], isr_ns: int|null, isr_percentage: number|null}`; `cpu_analysis.account` qualifies the full trace, while window shares come only from bounded observed scheduler intervals.
- Contention variant: `threshold_us: int`, `inversion_enabled: bool`, `resource_events: int`, `findings: [{kind: "Inversion"|"Long Wait", object: string, waiter: string, holder: string|null, holder_unknown: bool, duration_ns: int, explanation: string}]`.

The service caches only requests with identical trace-content fingerprint (actual stream/metadata modification times and sizes), selected build path, mode, and window/threshold parameters. Trace read failures, nonzero Python exit/stderr, and successful but incomplete reports are separate typed Java outcomes; any UI percentages are withheld on incomplete inputs, not presented as complete utilization figures.

### Installed Eclipse manual verification note

Not executed against an installed Eclipse product in this change: open each view from **Window > Show View** before selecting a trace and confirm that the permanent disclaimer and **No trace loaded** state appear with no Python invocation, CTF read, or target operation. Then disable each view in Zephyr Workbench preferences, reopen it, and verify that explicit loading is blocked with an actionable status. Repeat with a missing managed Python interpreter, a CTF folder without `metadata` or `channel0_0`, a trace containing no switch events, and a truncated CTF; the UI must not present an empty table as a passed analysis.
