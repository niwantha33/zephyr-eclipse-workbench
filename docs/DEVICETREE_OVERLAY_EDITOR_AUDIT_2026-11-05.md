# Devicetree overlay editor — source audit, feature comparison and implementation

This report covers the native Eclipse/Tycho **Zephyr Eclipse Workbench**,
and compares it to Kyle Bonnici's **DTS Language Server** and Mylonics'
**IDE for Zephyr** extension for VS Code. It distinguishes implemented features
from future work. No LSP parity or a successful hardware build is asserted
without corresponding native Eclipse and real West validation.

## Correct Zephyr model

An `.overlay` file **is not an independent compiled device tree**. The effective
tree is generated by Zephyr after preprocessing the board/SoC DTS, includes,
shields and selected overlays. Merely creating `app.overlay` does not prove
its content is included. Zephyr's default selection checks SoC/board overlays
before falling back to `app.overlay`; explicit `DTC_OVERLAY_FILE` changes
that selection. `EXTRA_DTC_OVERLAY_FILE` adds later overlays, preserving
primary selection (and giving the added files later precedence).

This workbench therefore distinguishes:

- **confirmed active:** a regular `.overlay` file found in this build's
  `zephyr/zephyr.dts.d` preprocessor dependencies, after checking the exact
  CMake cache `ZEPHYR_BASE`;
- **confirmed absent:** the selected build has dependency evidence but the
  opened overlay is not among the inputs;
- **unverified:** the selected build has not produced its cache or dependency
  evidence, or belongs to a different Zephyr checkout.

The `build_info.yml` file is *supplemental*: its include/binding directory
lists are read conservatively and do not override the actual dependency graph.
Malformed or unavailable metadata gives a clear explanation rather than
fabricating a board, binding or overlay. Contexts are cached by build/profile
path and the size/mtime of the cache, dependency file and build metadata.
Refreshing or reconfiguring a build changes those signatures.

## LSP choice

Kyle Bonnici's `devicetree-language-server` provides definitions, references,
declarations, hover, diagnostics, completion, semantic tokens, formatting and
more using explicitly configured contexts (`dtsFile`, `overlays`,
`includePaths`, `zephyrBindings`). Mylonics' IDE for Zephyr manages
workspaces, boards, build profiles and per-build overlays, whereas its VS
Code extension pack can bring in the separate DTS language server. A separate
Workbench for Zephyr extension demonstrates reading `build_info.yml` to
create those contexts.

**Decision for this PR:** extend the already packaged, offline-compatible
native editor and selected-build evidence path; do **not** silently install
Node, npm packages, an external VS Code extension, or LSP4E. A subsequent
separately qualified optional LSP4E adapter should (1) negotiate the exact
server configuration protocol/version, (2) construct per-build contexts, (3)
monitor workspace/overlay/build metadata, and (4) prevent stale diagnostics
from being presented as current. This PR is **not** full DTS-LSP parity.

## Use: normal overlays

1. Open a managed Zephyr application and select its exact board/profile.
2. Create or edit `app.overlay` (or the board/SoC-specific overlay chosen by
   Zephyr). The editor never invents pins or addresses.
3. Build/reconfigure. The generated `zephyr/zephyr.dts.d` is used to
   distinguish active overlays from inactive candidates. A yellow annotation
   on an inactive overlay reports the selection conflict without popping up
   hints. Syntax errors remain underlined.
4. Ctrl+click a known `&label` to open a matching source declaration from
   that build's preprocessor dependencies. If the original cannot be located,
   navigate to the exact last generated `zephyr.dts` instead.

## Use: explicitly selected additional overlays

Only when you want extra files beyond Zephyr's automatic selection, create:

```properties
# <application>/.zew/overlay-selection.properties
extra=boards/my-board-extra.overlay;overlays/my-peripheral.overlay
```

The paths must be existing, regular, application-owned `.overlay` files.
No relative traversal, symlinks, duplicate entries or absolute paths are
accepted. The builder adds a single
`-DEXTRA_DTC_OVERLAY_FILE:STRING=<absolute-file>;<absolute-file>` argument
when the selection is nonempty. It retains any primary automatically chosen
board, SoC or application overlay. Immediately after a successful Zephyr
configure it verifies that each selected extra overlay actually appears in
`zephyr.dts.d`; otherwise it fails with the file and a clear diagnostic.

**Compatibility:** if this optional file is absent, the workbench adds **no**
overlay CMake argument and does not replace an existing user setting. To clear
a selection while keeping the file, use `extra=` and review any previously
cached CMake value; use a pristine build if stale configuration persists.

## Quiet editor versus opt-in proposals

By default, the `.overlay` editor remains quiet (PR #159 behaviour):
no automatic completion, no hover pop-up and no advisory status banner.
To request optional manual completion and/or node hover in **this project**:

```properties
# <application>/.zew/devicetree-editor.properties
completion=true
hover=true
```

Reopen the editor to take effect. Even when enabled, suggestions appear
only when explicitly invoking Ctrl+Space; no keystroke-triggered list appears.
This is project-local and doesn't change the C/C++ editor or other projects.

## Validation and limits

- Pure-Java core tests check active/absent/unknown overlay claims, board/SoC
  identity, cache refresh, selected extra overlay CMake arguments, and traversal.
- The installed Eclipse editor smoke and a **fresh Windows multi-board firmware
  matrix** remain mandatory qualification checks, not implied by source changes.
- No pre-build analysis should claim a complete Zephyr parser: Zephyr's own
  CMake + C preprocessor + dtlib/edtlib + binding evaluation are authoritative.
- Metadata reading handles common scalar-list `build_info.yml` layouts, not
  all YAML anchors/inline values; it fails conservatively.
- Hyperlink navigation is first-source/last-generated fallback, **not** a
  full origin graph or complete cross-file LSP definition provider.
